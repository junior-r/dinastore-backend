# CLAUDE.md - Backend Development Guidelines

## 1. Backend Project Overview
This project is the backend API and services layer for an advanced e-commerce and print-on-demand platform for a custom clothing brand. It handles product catalogs, secure transactions, real-time messaging, custom image processing, gamification rules, and AI agent integrations.

## 2. Tech Stack & Environment
*   **Framework:** NestJS
*   **Language:** Strict TypeScript
*   **Runtime:** Node.js (latest LTS - v22+)
*   **Package Manager:** pnpm
*   **Database:** PostgreSQL
*   **ORM:** Prisma ORM
*   **Caching & Messaging:** Redis
*   **Real-time:** Socket.io (NestJS WebSockets module)

## 3. Architecture & Design Patterns
*   **Domain-Driven Design (DDD) / Hexagonal Architecture:** The codebase must be strictly organized by business domains (e.g., Catalog, Orders, Users, Customizations). Keep business logic decoupled from HTTP controllers and database adapters.
*   **CQRS (Command Query Responsibility Segregation):** Use the NestJS CQRS module to separate read operations (e.g., high-volume product catalog queries) from complex write operations (e.g., processing an order or handling a design upload).
*   **Repository Pattern:** Abstract all Prisma ORM calls through repositories so the domain layer remains agnostic of the database implementation.
*   **Clean Code:** Enforce strict typing, centralized error handling (exception filters), and strict environment variable validation (using Zod or Joi).

## 4. Core Domains & Features
*   **E-commerce Catalog & Orders:** Manage products, inventory, shopping cart validation, and secure payment processing (integrations for Stripe/MercadoPago).
*   **Customization Engine:** Handle user-uploaded designs, store them securely, and manage the logic for injecting/watermarking the mandatory store logo onto the designs before sending them to fulfillment.
*   **Gamification & Promotions:** Manage quiz states, validate answers, and handle the distribution of promotional codes and access to limited-edition drops.
*   **Real-Time Communications:** Manage WebSockets for live order tracking updates and the real-time customer support chat.
*   **Creative AI Agent Service:** Act as a bridge/proxy connecting the frontend to an AI instance. During development, this will interface with a local AI API (e.g., a local Ollama instance running Qwen) to assist users with design prompts.

### Implemented

- **Catalog domain** (`src/modules/catalog/`) — full DDD/CQRS vertical slice:
  - Prisma models: `Category`, `Product`, `ProductVariant`, `ProductImage`.
  - **Product ↔ Category is many-to-many** (migrated 2026-08-08 from a single required `categoryId`) — a Prisma implicit m2m (`_CategoryToProduct` join table), so a product can carry several tags (e.g. "Superheroes" + "Boys"). `Product.categoryIds: string[]` on the domain entity (invariant: at least one). The migration backfilled every existing product's old `categoryId` into the join table before dropping the column — see `prisma/migrations/20260808184002_product_categories_and_comments/migration.sql` if a similar backfill is ever needed again. Seeded categories beyond "Apparel": Superheroes, Villains, Cartoons, Boys, Girls.
  - Domain entity (`Product`) with invariants (price, name, at least one category, per-variant sku/size/color, no duplicate size+color) enforced via a `DomainError` — not a NestJS exception, so the domain layer stays framework-agnostic.
  - CQRS: `CreateProductCommand`, `GetProductsQuery` (paginated, clamps page/pageSize itself, not just at the DTO layer, filters by `categoryIds` with OR semantics — matches if the product has *any* of the requested categories), `GetProductBySlugQuery`, `GetCategoriesQuery` (flat list, no filters).
  - REST: `POST /catalog/products`, `GET /catalog/products` (`?categoryIds=id1,id2` comma-separated), `GET /catalog/products/:slug`, `GET /catalog/categories`. New products always start `DRAFT` — there is **no publish/admin endpoint yet**, so anything visible in the storefront right now was flipped to `PUBLISHED` by hand via SQL. Categories are seeded directly in the DB — still **no category create/edit/delete endpoint**.
  - Connecting a product to a category id that doesn't exist now surfaces as **404** (Prisma `P2025` on the `categories: { connect }` write), not 400 — different from the old required-FK behavior, which was a 400 (`P2003`) at insert time.
- **Users/Auth domain** (`src/modules/users/`):
  - `POST /auth/register`, `POST /auth/login`, `GET /auth/me` (JWT-guarded).
  - Password hashing via Node's built-in `crypto.scrypt` (`ScryptPasswordHasher`) — deliberate choice over bcrypt/argon2 to avoid native-module compilation on Windows.
  - `JwtStrategy` is stateless (validates signature/expiry only, no DB round-trip per request).
  - `Role` (`CUSTOMER`/`ADMIN`) exists on `User` but nothing enforces it yet — there are no role-gated routes.
  - **OAuth login** (`GET /auth/google`, `GET /auth/google/callback`) — `User.passwordHash` is now `String?`: OAuth-only users have no password. A new `OAuthAccount` model (`provider` + `providerAccountId`, unique together) links to `User`; `OAuthLoginHandler` tries, in order: sign in if that provider account is already linked → link the provider to an existing user found by email → create a brand-new `CUSTOMER` user. The callback redirects to `{FRONTEND_URL}/auth/callback?token=<jwt>` (a plain query-string JWT, not a one-time code — consistent with this project's existing "JWT in localStorage" security posture, but worth hardening before any real production use).
  - **Extending to another provider (GitHub/Spotify/Apple)**: the `OAuthProvider` enum already has all four members. Add a Passport strategy (see `infrastructure/auth/google.strategy.ts`) whose `validate()` returns the shared `OAuthProfile` shape (`infrastructure/auth/oauth-profile.ts`), add its two routes to `OAuthController` mirroring the `google`/`google/callback` ones, register the strategy in `UsersModule`, add `<PROVIDER>_CLIENT_ID`/`_SECRET` env vars. Nothing else needs to change — `OAuthLoginCommand`/`Handler` and the frontend's `OAUTH_PROVIDERS` config are already provider-agnostic.
  - **Real Google credentials are configured and Google login is confirmed working end-to-end** (`GoogleStrategy` falls back to placeholder values, not `getOrThrow`, only so an unconfigured app still boots — that fallback path is no longer what's in use).
  - **Avatar photo** — `User.avatarUrl` (`String?`) is populated **only** from an OAuth provider's profile photo; `User.create()` (password registration) has no `avatarUrl` field on its input type at all, so there is no code path for a password-only account to ever get one. `GoogleStrategy` reads `profile.photos[0].value`. Filled in at first creation (`createFromOAuth`), and separately via `UserRepository.setAvatarUrlIfMissing` — called on **every** OAuth login (existing-linked, and link-by-email) so an account created before this field existed (as some real ones now are) or before the provider had a photo picks one up as soon as it's available. It never overwrites an avatar the user already has.

The generator is pinned to `moduleFormat = "cjs"` in `schema.prisma` (Prisma's ESM-only default output broke the CJS project — see git history if this trips anyone up again).

  - Tests: unit tests for the entity + all four handlers (mocked repositories, `src/modules/orders/testing/`), plus `test/orders.e2e-spec.ts` (place order happy path, insufficient stock leaves stock untouched, DRAFT-product rejection, cross-user 404s, pay-twice rejection).
- **Admin site: roles, permissions, user management, full catalog CRUD** (added 2026-08-08/09) — first real authorization layer in the app:
  - `Role` gained `STAFF` (`CUSTOMER | STAFF | ADMIN`). `User` gained `isActive` (blocks login when false, checked in both `LoginUserHandler` and `OAuthLoginHandler`) and `permissions: string[]` (fixed enum, `src/modules/users/domain/entities/permission.ts`: `USERS_VIEW/MANAGE`, `PRODUCTS_VIEW/MANAGE`, `CATEGORIES_VIEW/MANAGE`).
  - **`RolesGuard`** (`modules/users/infrastructure/auth/roles.guard.ts`) checks the JWT payload's `role` claim only — no DB call, so a role change doesn't take effect until the user's token is refreshed (re-login). **`PermissionsGuard`** (same folder) bypasses entirely for `ADMIN`; for `STAFF` it does a fresh `UserRepository.findById` lookup every request, checking both `isActive` and `permissions` — so deactivation and permission grants/revocations take effect immediately on admin routes even with an already-issued token, unlike the rest of the site (see `JwtStrategy`'s statelessness note below). Applied via `@UseGuards(JwtAuthGuard, RolesGuard, PermissionsGuard)` + `@Roles(...)`/`@RequirePermission(...)` decorators.
  - **Role and permission changes are ADMIN-only** even for a STAFF user holding `users:manage` — enforced with a stricter `@Roles(Role.ADMIN)` on just those two routes, specifically so STAFF can't self-escalate. Self-modification (own role, own permissions, own deactivation) is blocked at the command-handler level (`DomainError`, 400) to prevent an admin locking themselves out.
  - `admin/users` (`AdminUsersController`): `GET /`, `GET /:id` (returns `oauthAccounts` + `hasPassword` via `UserRepository.findDetailById`), `PATCH /:id/role`, `PATCH /:id/permissions` (both ADMIN-only), `PATCH /:id/deactivate` / `PATCH /:id/activate` (`users:manage`).
  - `admin/catalog` (`AdminCatalogController`): `GET /products` (all statuses, unlike the public listing which defaults to `PUBLISHED`), `PATCH /products/:id` (name/description/price/currency/categories only — **deliberately does not touch variants**, to avoid regenerating variant ids and silently invalidating items already in customers' carts, which are keyed by `productVariantId`), `PATCH /products/:id/status`, `DELETE /products/:id`, `POST/PATCH/DELETE /categories`. Deleting a category rejects with 409 (naming the affected products) if any product would be left with zero categories (`CategoryRepository.findProductsThatWouldBeOrphaned`).
  - **Closed a real pre-existing hole**: the public `POST /catalog/products` was completely unauthenticated before this — it now requires `ADMIN`/`STAFF` + `products:manage`, same as the new admin routes, rather than duplicating a second create endpoint.
  - `UserResponseDto` (used by `/auth/register`, `/auth/login`, `/auth/me`, and every admin user endpoint) now also returns `permissions` and `isActive`.
  - Tests: `roles.guard.spec.ts`/`permissions.guard.spec.ts`, unit tests for every new command/query handler, `test/admin-users.e2e-spec.ts` (13 tests covering the full guard matrix — including STAFF-with-`users:manage`-still-blocked-from-role-change, and deactivating a STAFF user immediately blocking their still-valid token). 215 unit + 49 e2e tests passing.

- **Comments domain** (`src/modules/comments/`, added 2026-08-08) — full DDD/CQRS vertical slice, mirrors Orders' structure:
  - Prisma model: `Comment` (`productId`, `userId`, `body`, `createdAt`). Author name/avatar are read live via the `user` relation on the list query, not snapshotted (unlike `OrderItem`) — a comment should reflect the commenter's current profile.
  - `ProductLookupPort` (`domain/ports/product-lookup.port.ts`) — narrow read-only port into Catalog (`exists(productId)`), same pattern as Orders' `ProductCatalogPort`, so Comments doesn't depend on Catalog's `ProductRepository` directly.
  - **`CommentModerationPort` (`domain/services/comment-moderation.port.ts`) is the "respect policy" seam** — `CreateCommentHandler` depends only on this interface, `review(body): Promise<ModerationResult>` (async since 2026-08-08, see below).
  - **Comment moderation now calls the standalone `feelings-analysis` service** (sibling project, `../feelings-analysis`, added 2026-08-08) — a Python/FastAPI service that scores text with a **local** toxicity classifier (Detoxify, self-hosted, no third-party API/account/billing — switched 2026-08-08 from OpenAI's Moderation API after hitting its Tier-0 rate limit wall on an unfunded account). Wiring lives in `comments.module.ts`'s `COMMENT_MODERATION_PORT` factory:
    - `HttpCommentModerationAdapter` (`infrastructure/moderation/`) calls `POST {FEELINGS_ANALYSIS_URL}/v1/analyze` with an `X-API-Key` header (must exactly match feelings-analysis's own `SERVICE_API_KEY`) and a timeout (`FEELINGS_ANALYSIS_TIMEOUT_MS`, default 5000ms). It never guesses — any non-2xx (wrong/missing key → feelings-analysis's own immediate 401 before it does any processing, or a 500 if its classifier failed), network error, or timeout is thrown, not swallowed. The OpenAI→Detoxify swap changed nothing on this side — same response contract (`approved`/`score`/`triggered_categories`).
    - `FallbackCommentModerationAdapter` wraps it: on any thrown error it logs a warning and falls through to the original `KeywordCommentModerationAdapter` (still a small curated wordlist + shouting/harassment heuristics) — a bad key or an unreachable service degrades to local moderation, it never bypasses moderation entirely.
    - The factory only wires in `Http`+`Fallback` when **both** `FEELINGS_ANALYSIS_URL` and `FEELINGS_ANALYSIS_API_KEY` are set (same "don't crash on missing config" pattern as `GoogleStrategy`); otherwise `KeywordCommentModerationAdapter` is used directly with zero network attempts — this is why `pnpm test:e2e` needs no changes and no live feelings-analysis instance to pass.
  - CQRS: `CreateCommentCommand` (404 if the product doesn't exist, 400 via `DomainError` if moderation rejects the body, otherwise persists), `DeleteCommentCommand` (author-only; 404 not 403 on someone else's comment, same existence-hiding convention as Orders), `GetProductCommentsQuery` (paginated, newest first).

- **Product images can be tagged to specific variants** (added 2026-09-04) — lets an admin limit a photo to the variants it actually depicts (e.g. physical stock differs by color, so only the black-colorway photo should show when a customer picks black). `ProductImage` and `ProductVariant` gained an implicit m2m relation (`variants`/`images`, migration `20260905004136_product_image_variants`) — an image with **no** rows there applies to every variant, which is the default for an untagged image.
  - `ProductImageProps.variantIds: string[]` on the domain entity. Images arrive from `POST /catalog/products` before variant ids exist (both are created in the same request), so `CreateProductImageDto.variantIndexes?: number[]` references positions in that same request's `variants` array; `Product.create()` resolves indexes to the freshly-generated variant ids (throws a `DomainError` — 400 — on an out-of-range index) and is the only place this resolution happens.
  - `PrismaProductRepository.create()` connects each image's `variants` relation in the same nested `product.create()` write as the variants themselves — confirmed via `test/catalog.e2e-spec.ts` against real Postgres that Prisma orders the nested writes correctly (variant rows exist before the image-side `connect` needs them), rather than assuming it and reaching for an explicit `$transaction` split.
  - `productInclude.images` now also includes `variants: { select: { id: true } }`, ordered so `toDomain()` can map straight to `variantIds`. `ProductResponseDto.images[].variantIds` is the wire shape the frontend consumes.
  - Editing images/variants after creation still isn't possible from the admin UI (pre-existing gap, unchanged by this — `UpdateProductCommand`/`update-product.dto.ts` still only touch name/description/price/currency/categories), so this tagging only happens at product-creation time for now.
- **Variants and images are now editable after creation** (added 2026-09-04, closes the gap the bullet above left open) — two new endpoints, deliberately separate from `PATCH /admin/catalog/products/:id` (same "different concerns" split `Product.update()`'s own comment already argued for regarding variants).
  - `PATCH /admin/catalog/products/:id/variants` (`UpdateProductVariantsCommand` → `Product.updateVariants()`): full-replace semantics, same as `categoryIds` — the submitted array *is* the desired end state, so any existing variant (by id) left out gets deleted. An entry with `id` can only change `stock`/`priceCents`; `size`/`color`/`sku` are **locked** once a variant exists (the DTO's `@ValidateIf(o => !o.id)` doesn't even accept them for an existing entry) — deliberately, to sidestep a real edge case: renaming two variants' colors to swap them in one request would transiently violate `@@unique([productId, size, color])` mid-transaction (delete-then-upsert isn't ordered to avoid this). An entry with no `id` creates a new variant with the full shape, exactly like `create()`.
  - `PATCH /admin/catalog/products/:id/images` (`UpdateProductImagesCommand` → `Product.updateImages()`): same full-replace semantics, but with none of the above restriction — images carry no downstream referential risk (confirmed via `OrderItem.productVariantId` having **no FK at all** — it's a bare column, deliberately, per the snapshot comment on that model — and cart items snapshot everything at add-to-cart time, see frontend notes), so every field on an existing entry is freely editable. `variantIds` here are the variants' **real ids**, not `create()`'s index scheme — by the time a product is being edited every variant already has a real id, so there's no need to resolve anything.
  - `PrismaProductRepository.updateVariants()`/`updateImages()` both do delete-left-out-rows + upsert-the-rest inside one `$transaction`, confirmed against real Postgres (`test/catalog.e2e-spec.ts`) including the full add/edit-stock/remove/re-tag/full-replace-omission paths and both domain rejections (unknown variant id, image tagged to a variant id that doesn't belong to the product) surfacing as 400 via `DomainErrorFilter`.
  - Deleting a variant is safe for anything already referencing it: `PlaceOrderCommand` cleanly 404s if a `productVariantId` no longer resolves (`place-order.handler.ts`, via `ProductCatalogPort.findVariantsByIds`) rather than crashing, and the `_ProductImageVariants` join table cascades on variant delete (any image left with zero tagged variants just reverts to "applies to all", not orphaned).

- **Comment likes and 3-level replies** (added 2026-09-30, frontend counterpart in the frontend's progress log):
  - Migration `20261001015352_comment_likes_and_replies`. `Comment` gained a self-relation (`parentId`/`parent`/`replies`, `onDelete: Cascade` — deleting a comment takes its whole subtree with it) and a denormalized `depth` (1..3). New `CommentLike` model keyed `@@id([commentId, userId])` — that composite is what makes liking idempotent.
  - **`MAX_COMMENT_DEPTH = 3` and the flattening rule live on the entity, in `Comment.reply()`** — not in the handler. A reply sits one level below its parent, *except* at depth 3, where it is re-parented to the parent's own parent and stays at depth 3 (the Reddit/YouTube model). So the tree is bounded but nothing is ever un-replyable, and there is no depth at which the UI has to hide the Reply button. `reply()` also inherits `productId` from the parent, which makes a cross-product reply impossible by construction.
  - `CreateCommentCommand` gained `parentId`; the handler 404s on a parent that doesn't exist **or belongs to another product** (existence-hiding, same convention as `DeleteCommentHandler`). Moderation still runs on replies.
  - `SetCommentLikeCommand` (one command, a `liked: boolean`, rather than a Like/Unlike pair) → `POST`/`DELETE /catalog/products/:productId/comments/:commentId/likes`. Both verbs are idempotent, so a retry or double-click can't flip the state back; the response always carries a **re-read** `likeCount` rather than an arithmetic guess, so a stale tab converges on the real total. Liking your own comment is deliberately allowed.
  - **`PrismaCommentLikeRepository.like()` swallows P2002.** Prisma's `upsert` is a read-then-write, not one atomic statement, so two *concurrent* likes of the same comment both find no row and both insert — the loser got a P2002 that `PrismaExceptionFilter` turned into a 409. Found live by clicking the heart rapidly in the UI; the colliding row is exactly the row the request wanted, so it is a success. Covered by the two `survives concurrent …` e2e tests (verified they fail without the fix).
  - **`GET` is now behind `OptionalJwtAuthGuard`** (new, `users/infrastructure/auth/`) + `@OptionalCurrentUser()` (new decorator, kept separate from `CurrentUser` so the many genuinely-guarded routes don't have to start null-checking). The list stays public — counts are visible to everyone — but a token, when sent, fills in `likedByViewer`. A malformed token is ignored rather than 401ing.
  - **Pagination now applies to root comments only**, so a thread is never split across pages: `findByProduct` returns the page's roots plus every descendant, each root immediately followed by its own subtree. `PaginatedComments` therefore has both `total` (every comment, what the UI displays) and `rootTotal` (what `page`/`pageSize` index into). The repository walks the tree in two extra flat queries rather than a recursive CTE — depth is capped at 3, so a root's whole subtree is two hops away.
  - Tests: 260 unit (was 215) + 74 e2e (was 49) passing, including the depth/flatten rule on the entity, the parent-validation paths, per-viewer `likedByViewer`, and the concurrency regressions above.

- **One image per comment, behind a storage-agnostic port** (added 2026-10-01, frontend counterpart in the frontend's progress log):
  - **`FileStorage` port** (`shared/domain/storage/file-storage.port.ts`: `put`/`delete`/`publicUrl`, token `FILE_STORAGE`) provided by the global `StorageModule` (`shared/infrastructure/storage/`), which is the **only** place a backend is chosen (`STORAGE_DRIVER`, default `local`; an unknown value fails at boot). Only `LocalDiskFileStorage` exists. **To add S3/R2/GCS: one class implementing `FileStorage` + one `case` in `storage.module.ts` — nothing else changes.**
  - **The database stores storage *keys*, never URLs** (`comments.image_key`, `image_thumbnail_key`, `image_width`, `image_height`, migration `20261001120000_comment_image` — hand-written because Docker was down at the time, then confirmed with `prisma migrate diff` to match the schema exactly). `GetProductCommentsHandler` turns keys into URLs at read time via `fileStorage.publicUrl()`, so changing backend or adding a CDN (`STORAGE_PUBLIC_URL`) needs no data migration. The create response therefore carries only `hasImage`, not URLs — same "list-only" precedent as `author`.
  - "One image" is enforced twice: structurally (a single nullable slot on `Comment`, not a collection) and at the HTTP edge (`FileInterceptor('image', { limits: { files: 1 } })` → a second file is a 400). `POST …/comments` accepts **either** JSON or multipart on the same route (multer ignores non-multipart bodies); the file is held in memory (8 MB cap, `MAX_COMMENT_IMAGE_BYTES` → 413) and passed to the command as a `Buffer`.
  - **`ImageProcessor` port** (`shared/domain/images/`) → `SharpImageProcessor`: format is sniffed from the bytes (PNG/JPEG/WebP only — the client's Content-Type is never trusted), EXIF orientation is baked in and **all metadata stripped** (GPS!), `limitInputPixels` guards against decompression bombs, output is WebP in two renditions defined in `comments/domain/comment-image-policy.ts` (full ≤1600px q80, thumbnail ≤480px q72). Failures throw `InvalidImageError` (a `DomainError` → 400). `sharp` ships prebuilt binaries, so no native compilation on Windows.
  - `CreateCommentHandler` only processes the image **after** the product/parent/moderation checks pass, and deletes the stored files again if either upload or the DB insert fails. `DeleteCommentHandler` reads `CommentRepository.findImagesInSubtree()` **before** the delete (the cascade takes the replies' rows, and with them their keys), then removes files best-effort — a storage failure is logged, never thrown.
  - **Caching**: keys are random and never reused, so files are immutable. `main.ts` serves the local storage dir with `Cache-Control: public, max-age=31536000, immutable` (this also covers product images, whose names are random UUIDs too); `put()` passes the same header value for backends that store it per object.
  - Tests: 293 unit (was 260) + 84 e2e (was 74). The e2e suite uploads real images against the local driver and asserts on the files on disk. **Windows gotcha found while writing them:** `sharp(path)` keeps the file handle open, which makes a later delete of that file fail — read into a Buffer first.
  - **Known gaps:** deleting a *product* or a *user* cascades their comments at the DB level without going through `DeleteCommentHandler`, so those comments' image files are orphaned in storage. Product images (`catalog/infrastructure/uploads/product-image-storage.ts`) still write to disk through multer directly and store full URLs — not migrated to the port. No rate limit on uploads, and image *content* is not moderated (only the comment text is).
  - Unrelated things noticed: `multer` is imported by that product-image file but is not a direct dependency — it only resolves because pnpm's bin shims set `NODE_PATH`, so `pnpm start` works but a bare `node dist/src/main` does not. And `start:prod` points at `dist/main`, while the build emits `dist/src/main`.

- **Analytics domain: product-view history** (added 2026-10-04, `src/modules/analytics/`, frontend counterpart in its progress log). Full detail in `docs/features/analytics.md`; the parts worth knowing before touching it:
  - New table `product_views` (migration `20261005011743_add_product_views`, purely additive). One row per visit to a product page: product (+ name snapshot, `SetNull` on delete, same reasoning as `OrderItem`), `userId` (null when anonymous), `visitorId` (random per-browser id), `ipAddress`, `country`, `durationMs` (visible time only), `favorited`.
  - `POST /analytics/product-views` is **public** (`OptionalJwtAuthGuard`) and is one idempotent upsert keyed on a browser-generated `viewId`, used for both the opening report and every top-up. It is one operation on purpose: the page's first report and an early heartbeat can cross on the network, and "here is the visit's running total" is correct in either order. `PrismaProductViewRepository.save` handles the resulting P2002 race the same way `PrismaCommentLikeRepository.like` does.
  - **IP and country never come from the request body.** IP is `request.ip`; country is resolved in-process by `GeoIpCountryResolver` (new dependency `geoip-country`, a bundled offline database, so no visitor address leaves the server). The e2e spec proves a caller-supplied IP, country, user id, `X-Forwarded-For` and `CF-IPCountry` are all ignored when no proxy is trusted.
  - **New env var `TRUST_PROXY`** (`main.ts`, parsed by `shared/infrastructure/http/client-origin.ts`). Unset by default. **Must be set in production behind a proxy**, or every row records the proxy's address. It also gates whether `CF-IPCountry` is believed.
  - **Local development always records `::1`/`127.0.0.1` and a null country.** That is correct (loopback has no country), not a bug. Do not "fix" it.
  - New permission `Permission.ANALYTICS_VIEW` (`analytics:view`) guards `GET /admin/analytics/product-views`. Separate from `products:view` deliberately: this data includes visitor IPs tied to accounts.
  - Domain rules live in `ProductView.progress()`: duration only grows (late reports can't shrink it), capped at 4 h; IP/country/product/visitor are fixed at open; a user can be attached mid-visit but never swapped. A report with the wrong `visitorId` or `productId` for an existing view gets 404, indistinguishable from an unknown id.
  - Tests: 52 unit tests in the module + `client-origin.spec.ts`; `test/analytics.e2e-spec.ts` (24 tests) cleans up everything it creates. Full unit suite green (57 suites, 345 tests). **The other e2e specs were not re-run** for this change: several of them leave rows behind in the dev database (the "E2E Apparel" categories visible in the storefront came from them), so only the new spec was run.

- **Reviews domain: star ratings with an optional comment** (added 2026-10-07, `src/modules/reviews/`, frontend counterpart in its progress log; full write-up in `docs/features/reviews.md`).
  - New table `product_reviews` (migration `20261007120000_add_product_reviews`, purely additive, applied to the dev database). `@@unique([productId, userId])`: one review per shopper per product. `rating` is 1..5 whole stars, `body` is nullable.
  - **Separate from Comments on purpose.** A comment is a message in a thread; a review is one score that feeds the average. A review's comment is not part of the comment thread.
  - `GET /catalog/products/:productId/reviews` (public, `OptionalJwtAuthGuard`) returns `items` (**only reviews with a comment**, most recently edited first), `summary` (`average`, `count`, `distribution`, covering every rating) and `viewerReview` (the caller's own, since a bare rating is not in `items`). `PUT …/reviews/mine` creates or replaces the caller's review; `DELETE …/reviews/mine` removes it and is a 204 either way. Reviews are addressed by (product, caller), never by id, so no route can name someone else's.

### If you're about to touch this again

- Read the domain layer (`domain/entities`, `domain/repositories`) before the infra layer — the repository interfaces are the contract; Prisma specifics live only in `infrastructure/`.
- Follow the existing module structure (`domain/ → application/ → infrastructure/ → presentation/`) for any new domain — Catalog, Orders, and Comments are the reference implementations (Comments is the smallest end-to-end example of the narrow-port pattern: `ProductLookupPort`).
- Run `pnpm test && pnpm test:e2e` (Docker must be up) before considering anything done — both are fast and catch real regressions, not just type errors.
- **If you ever hand-seed a category/product/variant via raw SQL, use `gen_random_uuid()` for the id — never a hand-typed placeholder like `55555555-5555-5555-5555-555555555555`.** The Apparel category and the Classic Tee/Hoodie demo products were originally seeded that way; `class-validator`'s `@IsUUID()` (on `categoryId` and `productVariantId` DTOs) correctly rejects malformed ids like that, which made every order against them fail with `productVariantId must be a UUID`. Fixed on 2026-08-04 by deleting and recreating them (same names/prices/variants/images, real ids this time) — see git history / `docker exec dinastore-postgres psql -U dinastore -d dinastore` if a similar issue resurfaces.
